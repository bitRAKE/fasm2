#Coding Policy

This project is a fasm2 Win64 GUI application. Prefer small, local changes that match the existing assembly style and keep application state explicit.

#Build Validation

  • Build from a Visual Studio developer environment.
  • Use _build.cmd as the normal executable validation path.
  • Treat assembler success as necessary but not sufficient for UI or persistence changes; run a focused smoke test when behavior changes.

#Calling Convention

  • Use fastcall for local proc labels.
  • Use invoke for imported APIs and function pointers.
  • Spill proc arguments at entry before calls if they are needed later; proc parameter labels are home-slot addresses, not live register aliases.
  • Use addr local for out-parameters instead of preloading volatile argument registers and passing those registers positionally.
  • The project uses the RSP-based proc64.inc frame macros, so rbp is available as a normal nonvolatile register. Add rbp to the uses list before using it. It is a good choice for stable pointers to local structures or context structures, because [rbp+field] encodings are often smaller than the equivalent high-register addressing. This does not change the rule above: proc parameter labels are still home-slot addresses, not register aliases.

#Abstraction Boundaries

  • Do not add a proc, macro, or helper that only renames a single API call or replaces one obvious line with another single line.
  • An abstraction must remove real duplication, hide a fragile calling convention, centralize a tested algorithm, own state or lifetime, or provide a clearer contract than the raw call site.
  • Prefer direct Win32 calls for one-off setup and obvious operations, especially when the helper body would be only invoke SomeApi,... plus ret.
  • If a helper exists only to make a call look uniform, delete it and keep the call site explicit.

Avoid wrappers like this:

proc RedirLoadMsftEdit
        invoke  LoadLibraryW,'msftedit.dll'
        ret
endp

#String Handling

The project includes win64wx.inc, so the default inline string materializer matches wide-character TCHAR strings. windows.inc provides an A/W-dispatching fastcall.inline_string:

  • Plain literals use the active TCHAR flavor.
  • <A,'text'> forces ANSI.
  • <W,'text'> forces wide characters.
  • GLOBSTR.reuse and GLOBWSTR.reuse deduplicate repeated inline literals.

For APIs that have generic A/W aliases, prefer the generic API name with an undecorated literal:

invoke  LoadLibrary,'user32.dll'
invoke  MessageBox,[hMain],'Saved.','rtfedit',MB_OK

Use decorated API names only when the call genuinely requires that specific entry point or when the argument is not a string literal and the code is already explicitly wide or ANSI:

invoke  GetSaveFileNameW,addr ofn
invoke  SendMessageW,[hRichEd],EM_STREAMIN,[stream_flags],addr estr

Use explicit string materializers only when the Windows contract requires a specific byte format. The important current example is GetProcAddress, whose export-name argument is ANSI:

invoke  GetProcAddress,rax,<A,'RegDeleteTreeW'>

Do not keep ordinary call-site text in the data section. If a string is only passed to invoke or fastcall, put it directly at that call site:

fastcall ConsoleAppendMessage,'terminal','warning','cancel requested',0x00008080
invoke   wsprintf,console_wide_buf,'process exited with code %u',eax

Keep a named data-section string only when a stable address is required outside the argument materializer. Current valid cases include:

  • structure initializers such as WNDCLASSEX.lpszClassName;
  • MRUINFO.lpszSubKey registry subkeys;
  • OPENFILENAME filter and default-extension pointers;
  • pointer tables, such as font candidate lists;
  • mutable buffers and runtime-built text storage.

Literal class names are still string values. For example, RICHEDIT50W is the registered RichEdit class name, but the API call should still use the generic dispatcher unless a specific API flavor is needed:

invoke  CreateWindowEx,0,'RICHEDIT50W',0,...

#Data Ownership

  • MRU blobs should own persisted identity and comparison keys.
  • UI labels may be derived from MRU blobs but should not become hidden identity unless that is the documented policy.
  • Keep scratch buffers global only when they are shared by existing code paths or required by Win32 structures; prefer locals for short-lived state.
  • Module-level global storage registers itself through __GLOBAL_DATA__ and __GLOBAL_BSS__, then is emitted by the central GLOBAL_EMIT_DATA / GLOBAL_EMIT_BSS section points. This is the repo-wide data/BSS policy: do not add new feature-specific section emitters or direct feature data macro calls in rtfedit.asm.
  • Keep initialized constants and nonzero defaults in the data emitter; keep zero or uninitialized storage in the BSS emitter.
  • Feature emitters must own their alignment. Do not assume the previous emitter ended on a useful boundary; start BSS emitters with align 8, and add local align directives before qword tables or structures that follow byte/word buffers or 32-bit fields.
define __GLOBAL_DATA__ feature_data
define __GLOBAL_BSS__  feature_bss

macro feature_data
  feature_name du 'example',0
  align 8
  feature_default dd -1
end macro

macro feature_bss
  align 8
  feature_handle dq ?
  feature_buffer rw 260
end macro

#Resource IDs

Resource and control IDs shared by assembly and the Windows resource compiler live in rtfedit.h. This file is included by both windows.inc and rtfedit.rc, so it is the single source of truth for menu, dialog, icon, dynamic-range, and child-control IDs.

Keep rtfedit.h intentionally austere:

  • only #define NAME value lines;
  • no comments;
  • no include guards;
  • no blank policy prose or assembler-only expressions;
  • use numeric constants that both fasm2 and rc.exe accept.

Do not duplicate resource IDs in rtfedit.rc or windows.inc. Derived assembly-only constants, such as range sizes, may stay in windows.inc after the shared include.

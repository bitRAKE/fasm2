# conio

`examples/conio` is a console event-discovery program, but its more important
role in the example set is language experimentation. Unlike most Win32 samples
in this repository, it does not emit a PE executable directly. It emits a
Microsoft x64 COFF object plus a generated linker response file, then lets the
Microsoft linker produce the final console executable.

The program opens the real console handles, switches input/output modes, enters
the alternate screen buffer, reads `INPUT_RECORD` values with
`ReadConsoleInputA`, and displays keyboard, mouse, window-size, menu, and focus
events with VT escape sequences. Press `Esc` twice to exit.

## Build

Run from a Visual Studio x64 developer prompt:

```cmd
cd C:\git\fasm2\examples\conio
_build.cmd
```

The build script does two steps:

```cmd
call "..\..\fasm2.cmd" -e 5 conio.asm
link @conio.response
```

The first step writes `conio.obj` and `conio.response`. The second step passes
the generated response file to `link.exe`.

## Why This Example Is Unique

Most examples either assemble a complete executable with `format PE64` or use a
more conventional Win64 include stack. `conio` deliberately does something
different:

- `console.inc` starts with `format MS64 COFF`, so fasm2 emits an object file.
- Linker settings are generated by fasm2 source into `conio.response`.
- Imported Win32 calls use a local `::Function` / `:library:Function` syntax.
- Data, BSS, and string literals are gathered by custom block macros.
- The main routine uses a stable global `RBP` frame as the program data model.
- Output strings are built through CALM line interceptors instead of ordinary
  procedure calls.

This makes `conio` a compact study of fasm2/fasmg language extension points,
not just a console API sample.

## Source Layout

`conio.asm` owns the application behavior: setup, event loop, event decoding,
terminal output, cleanup, and small numeric conversion helpers.

`console.inc` owns executable policy and the local language additions:
MS64 COFF format, generated linker response output, `<<...>>`, `<|...|>`, and
the custom Win32 call syntax.

`data_blocks.inc` owns late data emission: deduplicated string pools, explicit
ANSI/wide inline-string materialization, and the `≡`, `∵`, and `□` block
macros.

`wincon.g` is the local console API translation: `INPUT_RECORD`,
`KEY_EVENT_RECORD`, `MOUSE_EVENT_RECORD`, `CONSOLE_SCREEN_BUFFER_INFO`, console
mode flags, event constants, and related structures.

`conio.response` is generated output. It is useful to inspect, but it should be
understood as build product from `console.inc`.

## MS64 COFF Instead Of Direct PE

The first line of `console.inc` is:

```asm
format MS64 COFF
```

That selects fasm2's Microsoft x64 COFF backend and `use64`. The source then
declares:

```asm
public Main as 'mainCRTStartup'
```

There is no CRT startup object and no default library search. The linker sees a
normal COFF symbol named `mainCRTStartup` and uses it as the console entry
point.

This example therefore tests an object-file workflow:

```text
conio.asm -> conio.obj + conio.response -> conio.exe
```

That is different from examples that assemble a finished PE image in one pass.
It lets the program use the Microsoft linker for final image policy while still
generating that policy from assembly source.

## Generated Linker Response

`console.inc` contains:

```asm
virtual as 'response'
        db '/NOLOGO',10
        ...
        db '/NODEFAULTLIB',10
        ...
end virtual
```

The named virtual output area writes `conio.response` next to the object file.
The response file includes the linker options and the object path.

The current policy is intentionally small and explicit:

- `/NODEFAULTLIB` avoids CRT/default-library participation.
- `kernel32.lib` is requested only because the source used a `:kernel32:...`
  call form.
- `/SUBSYSTEM:CONSOLE,6.02` sets the console subsystem version.
- `/FIXED` and `/BASE:0x7FFF0000` create a fixed image for this experiment.
- `/HEAP:0,0` and `/STACK:0,0` leave minimal reserve/commit policy to the
  linker defaults allowed by those switches.
- `/GUARD:NO`, `/CETCOMPAT:NO`, and `/HIGHENTROPYVA:NO` keep mitigation
  metadata out of this intentionally minimal image.

The response file also derives the object name from `__SOURCE__`, so the build
command only needs:

```cmd
link @conio.response
```

## Custom Win32 ABI Invocation

The program does not use the usual import table helpers. Instead, `console.inc`
defines a CALM line interceptor for two call forms:

```asm
:kernel32:GetStdHandle dword STD_INPUT_HANDLE
::GetStdHandle dword STD_OUTPUT_HANDLE
::WriteFile [.hOutput], rdx, r8, 0, 0
```

The library-qualified form records a library name and a function name. The
library-free form records only a function name. Both forms assemble as:

```asm
fastcall [Function], parameters
```

During `postpone`, every referenced function emits an external import pointer:

```asm
extrn '__imp_FunctionName' as FunctionName: QWORD
```

This is the COFF/MSVC import model: calls go through the linker-provided
`__imp_...` IAT slot, but source code can refer to a short `FunctionName`
symbol. The object file does not encode which library owns each function. The
generated response file supplies the libraries, and the linker resolves the
externals by normal library search.

In this example, one `:kernel32:...` call is enough to add `kernel32.lib` to the
response file. The later `::...` calls reuse the same library search result
without repeating the library name on every line.

## Static Fastcall Frames

The source uses fasm2's Win64 `fastcall` machinery as a frame-size calculator:

```asm
fastcall?.frame = 0
...
enter .frame + .local, 0
...
.frame := fastcall?.frame
```

Calls through `::Function` expand to `fastcall [Function], ...`. The macro
tracks the largest outgoing argument area needed by all such calls. The final
`.frame := fastcall?.frame` gives the earlier `enter` instruction a stable
allocation size after fasm2 resolves the forward reference.

The result is one static outgoing-call area for `Main`, not a stack adjustment
around every Win32 call. Smaller helper routines use the same idea locally
when they need to call Win32 APIs.

## Custom Data Model

`conio.asm` keeps `RBP` stable for the entire `Main` routine. The local frame is
declared with a virtual layout:

```asm
virtual at rbp - .local
        .bbuff          rb 256
        .oldInMode      dd ?
        ...
align.assume rbp, 16
align 16
.local = $ - $$
        .old_RBP        dq ?
        .RET            dq ?
        .hOutput        dq ?
        ...
end virtual
```

The labels inside this virtual block become addressable fields of `Main`.
Helpers can refer to them by qualified names such as:

```asm
Main.bbuff
Main.hOutput
Main.ctlkey_state
```

This is why comments call the `Main` frame "global." It is not global storage in
a data section. It is stack storage with stable symbolic offsets, shared by
leaf helpers that intentionally do not create their own `RBP` frame.

The layout also places a few frequently used fields after the saved `RBP` and
return address, in the parent shadow-space area. The source asserts that this
small group stays within that space:

```asm
assert $ - .hOutput < 33
```

That is a deliberate code-size/data-model experiment, not a general pattern for
large programs.

## Late Data Blocks

`data_blocks.inc` defines three visible block macros:

```asm
≡   ; readonly/constant data
∵   ; initialized data
□   ; uninitialized data
```

Example:

```asm
□       hInput          dq ?
□       hQuitEvent      dq ?
```

These are not sections by themselves. They are gatherers. Each use records a
source line, and a later `postpone` block emits all gathered lines in a stable
place:

- deduplicated wide and narrow string pools first;
- `≡` constant data next, currently allowed in the code section;
- `∵` and `□` after switching to a writable `.data` section when needed.

The macros align each block to a cache-line boundary and emit `.start`/`.end`
labels. At the end of assembly, they display byte counts for CONST, DATA, and
BSS.

The key idea is ownership without early section switching. A source module can
declare storage near the code that uses it, while the final object still gets a
controlled data layout.

## Inline String Materialization

`data_blocks.inc` also customizes `fastcall?.inline_string`:

```asm
macro fastcall?.inline_string var
        ...
end macro
```

String arguments to `fastcall` can be materialized as deduplicated ANSI or wide
strings. The macro recognizes explicit prefixes:

```asm
A, 'ansi text'
W, 'wide text'
```

Without an explicit prefix it chooses `GLOBWSTR` or `GLOBSTR` from
`sizeof.TCHAR`. The example mostly uses direct ANSI byte output, but this hook
is part of the local ABI surface because every `::Function` call eventually
passes through `fastcall`.

## Output Line Interceptors

`console.inc` defines two CALM handlers for source lines that would not
otherwise be instructions.

`<<...>>` writes a constant string immediately:

```asm
<< 27,"]0;","Input Debug Panel",7 >>
```

The handler creates a unique `GLOBSTR` object and assembles a `WriteFile` call:

```asm
::WriteFile [.hOutput], addr generated_string, sizeof generated_string, 0, 0
```

`<|...|>` appends constant fragments to the current output buffer at `RDI`:

```asm
<| 27,'[95m','KEY_EVENT',27,'[m',': ' |>
```

The handler materializes a `GLOBSTR`, then emits:

```asm
lea rsi, [generated_string]
mov ecx, sizeof generated_string
rep movsb
```

This is why the event decoder can read like text construction while still
reducing `WriteFile` calls. Most event paths build a line in `.bbuff`, then
flush the complete range once.

## Console Runtime Contract

At startup, the program:

- captures input/output handles;
- saves input and output code pages;
- switches both code pages to UTF-8;
- saves console input and output modes;
- enables mouse and window-size input;
- enables VT output processing;
- creates a manual-reset quit event;
- installs a console control handler;
- enters the alternate screen buffer.

The wait loop uses the adjacency of two BSS handles:

```asm
□       hInput          dq ?
□       hQuitEvent      dq ?

assert hQuitEvent = 8+hInput
```

That lets the code wait on both handles with:

```asm
::WaitForMultipleObjects 2, addr hInput, FALSE, -1
```

On normal exit it leaves the alternate screen buffer, restores the cursor
position, emits a linefeed for PowerShell prompt repair, restores console
modes, restores code pages, and exits with `ExitProcess`.

## Event Display Model

The event loop reads one `INPUT_RECORD` at a time. An `iterate` list maps
documented event types to local handlers:

```asm
iterate EVT, KEY_EVENT,MOUSE_EVENT,WINDOW_BUFFER_SIZE_EVENT,MENU_EVENT,FOCUS_EVENT
        cmp [.iBuffer.EventType], EVT
        jz .process_#EVT
end iterate
```

The handlers intentionally expose raw fields:

- key up/down state, repeat count, virtual key, scan code, Unicode character;
- mouse movement, button state, double-click and wheel flags;
- window buffer size;
- menu command ID;
- focus state;
- control-key state changes shown in a fixed overlay.

The example therefore doubles as a console input probe. It is useful when
checking how Windows Terminal, conhost, PowerShell, and different terminal
settings transform console input events.

## Language Features To Study

This example is a concentrated tour of fasm2/fasmg language additions:

- `format MS64 COFF` for object-file output.
- Named virtual output with `virtual as 'response'`.
- `postpone` to emit imports, data blocks, string pools, and response text only
  after all source usage has been seen.
- CALM line interception with `calminstruction ?` and `calminstruction ??`.
- `match`, `transform`, `take`, `publish`, `arrange`, and `assemble` to parse
  custom source forms and re-emit ordinary assembly.
- `namespace COFF` as compile-time state for unique libraries/functions.
- `mvmacro`-installed block gatherers for `≡`, `∵`, and `□`.
- `GLOBSTR`/`GLOBWSTR` string pooling with reuse enabled.
- `iterate` and token concatenation for compact event and table generation.
- `virtual at rbp - .local` for a named stack-frame data model.
- `align.assume` to tell fasm2 the intended base-register alignment while
  computing virtual layout.

The important lesson is that the additions are not hiding the machine. They are
local notations for repeated low-level decisions: where storage lives, how
imports are represented in COFF, how much outgoing stack space is needed, and
when constant text should be copied versus written immediately.
